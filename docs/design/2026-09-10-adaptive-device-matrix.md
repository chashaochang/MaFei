# MaFei 2.0 多形态设备适配矩阵

这份矩阵定义 MaFei 首页、详情、媒体库、设置与播放器共享的适配底座。机型用于覆盖极端形态和验收，不进入业务判断；运行时只依据当前可用窗口、宽高比、安全区、折叠姿态、内外屏角色和折痕/铰链区域决定布局。

## 0. 开发优先级

前期只实现三种常见窗口策略，不按品牌或具体产品写分支。折叠屏能力保留公共几何入口，等首页、媒体库和详情页在三种常见窗口上稳定后，再进入 P1 真机验收。

| 阶段 | 窗口族 | 代表验收尺寸（dp） | 当前目标 |
| --- | --- | --- | --- |
| P0 | 直板手机 | 360×800、390×844、430×932；横屏 800×360 | 底部导航、单栏 Hero、2 列海报；短横屏压缩 Hero，状态与滚动不重置 |
| P0 | 平板 | 744×1133、834×1194；横屏 1133×744、1194×834 | 导航轨、横向 Hero、3～5 列内容；旋转和分屏只重排，不重新加载 |
| P0 | PC | 最小 800×600、常用 1280×800、1440×900、连续缩放 | 窄窗退化到平板/手机策略；宽窗侧栏、内容限宽、键鼠与触控并存 |
| P1 | 折叠与多屏 | 外屏、内屏、半折、双 Pane、三 Pane | 接入平台折痕与内外屏事件，按安全分区布局并做真机验收 |

P0 的“手机 / 平板 / PC”是窗口策略，不是硬件身份。例如 PC 窗口缩到 520dp 时使用手机结构，平板分屏到 700dp 时使用平板结构；外接鼠标不会改变布局族。

### P0 统一适配规则

- 每次窗口宽高变化都重新计算布局；页面 ViewModel、登录会话、导航目的地、已加载数据和滚动状态放在布局之外。
- `Compact (<600dp)` 使用 Phone，`Medium/Expanded (600～999dp)` 使用 Tablet，`Large (≥1000dp)` 使用 Desktop。
- 高度小于 480dp 时进入短窗口策略：缩短 Hero、减少说明文字，但不缩小触控目标。
- PC 内容区设置最大宽度并居中，避免窗口越宽海报和行长无限增长。
- 平板横竖屏通过同一份布局函数连续变化，不维护两套页面。
- Hover、Focus、滚轮、触控和键盘是独立输入能力，不能作为 Phone / Tablet / Desktop 的判断条件。
- P0 页面不得读取 `deviceModel`、品牌或操作系统来选择布局。

## 2. 不能混为一谈的三个决策轴

### 布局轴

由当前可用窗口宽度、高度、宽高比、字体缩放、安全区和物理遮挡区域决定。设备品牌、型号、CPU、操作系统和是否接了鼠标都不能直接决定页面布局。

### 折展轴

由 `foldPosture`、`displayRole` 和 0～多个 `occlusions` 决定。内外屏切换、单屏/双屏/三屏变化只重算布局，不重建登录态、首页数据或当前路由。

### 输入轴

触控、鼠标、触控板、键盘和笔可以同时存在。Hover、Focus、Press、Scroll 分别响应真实事件；接入鼠标不能缩小触控目标，也不能切换成另一套“PC 页面”。

## 3. 公共几何契约

`common:design-system` 提供纯 Kotlin 输入与归一化结果：

- `MaFeiWindowEnvironment`：窗口宽高、字体缩放、安全区、折叠姿态、内外屏角色、物理遮挡区。
- `MaFeiAdaptiveWindow`：有效内容边界、宽高等级、宽高比类型、遮挡轴和安全内容分区。
- `MaFeiRectDp`：统一使用 Compose dp 坐标；平台桥接必须先把系统坐标换算到页面坐标。
- `panes`：普通设备为 1 个；书本折/双屏为 2 个；三折叠可为 3 个。基础算法不限制品牌和铰链数量。

宽度等级初始基线：`<600 Compact`、`600～839 Medium`、`840～1199 Expanded`、`≥1200 Large`。高度另分 `<480 Short`、`480～719 Medium`、`≥720 Tall`。首页不能只看宽度：短横屏、阔直板、小方外屏和半折状态必须同时参考高度、宽高比和安全分区。

## 4. 平台桥接职责

| 平台 | 薄宿主/平台模块提供 | 共享 CMP UI 负责 |
| --- | --- | --- |
| HarmonyOS | 窗口大小、安全区、内外屏/折展状态、当前折痕区域；三折设备可上报两个折痕 | 将事件归一化为公共环境，依据安全分区组织 Hero、网格、导航和浮层 |
| Android | 当前 WindowMetrics、系统安全区、平台提供的折叠特征和遮挡区域 | 与 HarmonyOS 共用相同宽高等级和 Pane 算法 |
| iOS/iPadOS | UIWindow/Scene 可用区域、安全区，以及系统对折叠/多屏形态提供的公开几何信息 | 不依赖机型名单；若系统只提供窗口变化，先保证响应式与状态连续 |
| Mac | Compose 窗口内容区、缩放与安全区 | 连续窗口缩放、最小尺寸、侧栏与内容限宽、键鼠交互 |

平台事件只更新环境数据，不触发服务器重新请求。页面选择、滚动锚点、输入内容、播放状态和缓存由各自状态持有者保存，布局切换只改变呈现。

## 5. 首页适配规则

- Compact Tall：底部导航、纵向 Hero、续播横向条、1～2 列海报。
- Compact Balanced/Short：缩短 Hero，首屏优先片名和主操作；长简介延后，避免底栏遮挡。
- Medium / Expanded：P0 统一为平板导航轨、横向 Hero 和较高内容密度；P1 再处理近方形折叠内屏的安全 Pane。
- Large：P0 使用完整侧栏与内容最大宽度，不让海报无限放大；P1 再加入 2/3 Pane 编排。
- Vertical hinge：文字、播放按钮、搜索、导航和卡片点击区不得跨过折痕。
- Horizontal hinge / HalfOpened：展示区与操作区分别落在上下安全 Pane，分界锚定真实折痕。
- Two hinges：支持三安全 Pane；关键操作至少在一个完整 Pane 内，不能横跨两个折痕。
- 外屏切内屏、旋转、分屏和 PC 缩放：保留当前路由、媒体库选择、滚动锚点、已加载数据和输入焦点语义。

## 6. 验收阶梯

1. P0 纯 Kotlin 单测：覆盖手机、平板旋转/分屏、PC 连续缩放、短窗口和大字号。
2. P0 Mac 窗口阶梯：360×800、390×844、800×360、744×1133、1133×744、800×600、1280×800、1440×900。
3. P0 Android/HarmonyOS/iOS：验证直板手机旋转、平板旋转/分屏、窗口断点与状态保持。
4. P1 纯 Kotlin 单测：补齐外屏、内屏、书本折、双屏、三折和半折安全区。
5. P1 折叠模拟或真机：验证真实内外屏切换、折叠姿态和折痕坐标，必须保存布局树/系统状态和截图证据。
6. 真机输入：手机和平板连接键鼠，验证 hover、焦点、滚轮和触控交替不改变布局或命中尺寸。

当前底座只建立公共几何与测试契约。各平台折叠信息桥接、折痕感知 Compose 容器和完整真机矩阵必须分批实现并分别验收，不能因 Mac 窗口缩放通过就宣布折叠屏适配完成。
