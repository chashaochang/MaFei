# 手机端性能与连续动效设计

状态：已获用户批准，待实现

## 背景

手机版主链路（首页/媒体库列表 → 影片详情 → 返回）已经可用，但快速滚动、图片陆续出现和页面切换仍有掉帧或突兀感。当前代码已有图片内存缓存、局部淡入、Navigation 3 页面滑入和详情页异步内容动画；本轮不重新设计页面，也不改变 Provider、Repository 或播放业务。

## 目标

1. 降低首页和媒体库列表快速滚动时的主线程工作，优先消除肉眼可见的卡顿。
2. 让首页/列表卡片进入详情时具有连续的封面过渡，返回时回到原卡片位置。
3. 图片、演员、季/集等异步内容采用稳定的局部渐进出现，避免整页闪烁或布局跳动。
4. 返回、快速重复点击和动画中再次导航都能取消旧动画并保持正确路由与滚动位置。
5. Android、iOS、HarmonyOS 和 macOS 继续使用同一套 Compose API；平台不支持共享元素时必须有普通导航动画降级。

## 非目标

- 不重写首页、详情页或播放器布局。
- 不改变旧鸿蒙版的数据字段、图片候选顺序或业务交互。
- 不给列表卡片批量添加玻璃、模糊、色散或全屏 backdrop。
- 不为开发版测试数据增加兼容逻辑。
- 不以桌面编译通过代替手机视觉和流畅度验收。

## 方案

### 1. 性能基线与修复边界

先以 Android 手机为主验收设备，记录以下四条路径的现象和耗时：首次进入首页、快速滚动海报网格、打开详情、从详情返回。代码检查重点为：

- 列表项是否有稳定 key，滚动状态是否被路由重建；
- 滚动帧中是否重复计算布局、图片候选或网络请求；
- 图片解码是否在主线程、是否重复解码同一 URL；
- backdrop、shader 和动画是否被列表项重复创建。

修复优先采用 `remember`、`derivedStateOf`、稳定参数和现有 `ArtworkMemoryCache`，只在有证据时修改解码尺寸、预取范围或动画时长。不得用增加全局延迟掩盖掉帧。

### 2. 卡片到详情的连续过渡

在现有 `NavDisplay` 的 `sharedTransitionScope` 能力上做单条试点：

- 给首页/媒体库卡片的主海报和详情 Hero 使用同一稳定媒体 ID；
- 只共享海报边界、圆角和裁剪，不共享整个卡片文字区；
- 前进时海报从卡片位置连续展开到详情 Hero，详情数据仍按现有异步流程加载；
- 返回时反向回到发起卡片，原列表的滚动位置由已有 `LazyGridState` 保留；
- 共享元素 API 在 OHOS、iOS 或桌面编译/运行不满足条件时，回退到当前滑入+淡出，不阻塞导航。

试点只覆盖影片/剧集主海报。演员头像、季卡片和播放页不在第一批，避免一次扩大动画协调范围。

### 3. 异步内容动效

保留详情页已有 `DetailAnimatedVisibility` 和图片 `Crossfade`，只做一致化：

- 加载占位到真实内容使用一次局部淡入/尺寸稳定，不清空已经显示的旧内容；
- 详情 Hero、演员区、季/集列表分别拥有独立的可见状态；
- 快速切换详情时取消旧请求的展示动画，避免旧内容在新页面闪回；
- 失败和空状态不使用加载动画伪装，沿用现有错误/空状态组件。

### 4. 导航和可中断性

保留 Navigation 3 的前进、返回和预测返回回调，只统一动效时序：前进使用短距离横向位移+淡入，返回使用反向位移；共享元素成功时由共享元素主导，普通页面内容使用轻微淡入。所有动画状态均绑定路由 key 或媒体 ID，返回时不依赖全局单例。

## 验收

- Android 真机：首页快速上下滚动、点击首屏和列表卡片、详情加载、连续打开两部影片、侧滑/系统返回；无明显跳帧、白闪、旧内容闪回或列表位置丢失。
- HarmonyOS 手机：同样四条路径，确认共享元素不导致崩溃；不支持时确认普通转场可用。
- iOS/macOS：至少编译并验证普通转场降级。
- 浅色/深色各验证一次；不截取用户整个桌面，只在需要视觉验收时截取应用窗口或使用布局树。
- 回归命令至少包括 `:composeApp:desktopTest`、Android 编译/单测，以及对应 Feature 的桌面测试。

## 风险与回退

共享元素动画属于 Compose 1.9/Navigation 3 的实验能力。若 OHOS 渲染器出现崩溃、裁切错误、首帧卡顿或返回失效，立即关闭该试点并保留现有 `NavDisplay` 转场；性能优化和异步渐进动画独立合入，不与共享元素绑定。
